= Computing a disc ID
:description: How AccurateRipDiscId is derived from per-track sample counts, and the maths behind discId1, discId2 and cddbDiscId.
:keywords: AccurateRip, disc ID, CDDB, TOC, dart

Before you can look anything up in the AccurateRip database, you need to identify the disc.
{project-name} does this with `AccurateRipDiscId`, computed purely from the sample count of every track — no CD drive access required once you have that data.

== The type

[source,dart]
----
class AccurateRipDiscId {
  const AccurateRipDiscId({
    required this.discId1,
    required this.discId2,
    required this.cddbDiscId,
    required this.trackCount,
  });

  final int discId1;
  final int discId2;
  final int cddbDiscId;
  final int trackCount;

  external factory AccurateRipDiscId.fromTrackSampleCounts(
    List<int> trackSampleCounts, {
    int sampleRate = 44100,
  });
}
----

Construct it directly if you already have the four field values from elsewhere, or — the common case — call `AccurateRipDiscId.fromTrackSampleCounts` and let {project-name} do the arithmetic.

== The input: per-track frame counts

`trackSampleCounts` is a list of per-track **stereo frame counts** — samples per channel, in track order, not raw byte counts and not mono sample counts.
One CD sector is 588 frames, so a track's length in sectors is `frameCount ~/ 588`.

You can obtain a track's frame count in a couple of common ways:

* From a WAV file: `extractPcmFromWav(wavBytes).lengthInBytes ~/ 4` (each stereo frame is 4 bytes — see xref:wav.adoc[]).
* From a FLAC file's `STREAMINFO` block: the `totalSamples` field is already a frame count.
* From the command line: xref:cli:disc-id.adoc[the `disc-id` command] computes and prints an `AccurateRipDiscId` from a set of WAV files directly.

`sampleRate` defaults to 44100 Hz, which is correct for every Red Book CD; there is normally no reason to pass anything else.

== The ID maths

Internally, `fromTrackSampleCounts` first turns frame counts into per-track **sector offsets** (`offset = frameCount ~/ 588`), with track 1 always starting at offset 0, then derives three different IDs from those offsets:

[cols="1,3"]
|===
| Field | Definition

| `discId1`
| The plain sum of every track's raw start offset, plus the lead-out sector offset. No lead-in bias.

| `discId2`
| The same sum, but each offset is weighted by its 1-based track index before summing; a zero offset (track 1) contributes `1` rather than `0` so it is not dropped by the weighting. The lead-out is weighted by `trackCount + 1`.

| `cddbDiscId`
| The legacy FreeDB/CDDB disc ID, packed as `(digitSum << 24) \| (totalSeconds << 8) \| trackCount`. This is the **only** one of the three that applies the standard 150-sector (2-second) lead-in bias to each offset before computing seconds.
|===

[IMPORTANT]
====
`discId1` and `discId2` use **raw** LBA offsets — track 1 genuinely starts at offset 0, with no 150-sector bias applied.
The 150-sector lead-in bias is a FreeDB/CDDB convention, and in {project-name} it is applied **only** inside the `cddbDiscId` calculation.

Releases up to 0.0.3 applied the 150-sector bias to all three IDs, which shifted every `discId1`/`discId2` away from the value the live AccurateRip server expects — every lookup URL built from a biased ID 404'd. Fixed in 0.0.4; do not reintroduce the bias into `discId1` or `discId2` if you are touching this code.
====

== Worked example

Take a 3-track disc with these per-track frame counts:

[cols="1,2,2"]
|===
| Track | Frame count | Sector offset (`~/ 588`)

| 1
| 13,371,228
| 0

| 2
| 11,908,704
| 22,740

| 3
| 9,847,200
| 42,992

| _(lead-out)_
| —
| 59,738
|===

[source,dart]
----
final id = AccurateRipDiscId.fromTrackSampleCounts([
  13371228, // track 1
  11908704, // track 2
  9847200,  // track 3
]);
----

This produces:

* `discId1` = `0 + 22740 + 42992 + 59738` = `125470` = `0x0001ea1e`
* `discId2` = `(1 × 1) + (22740 × 2) + (42992 × 3) + (59738 × 4)` = `413409` = `0x00064ee1`
* `cddbDiscId` = `0x1b031c03`
* `trackCount` = `3`

`discId1` and `discId2` feed directly into the lookup URL built by `buildAccurateRipUrl` — see xref:lookup.adoc[].
